# 別添：AIとアプリを作る実践プロンプト集

更新：2026-09-12／参加者用初稿

この資料は目的別に使う追加プロンプトです。既存のサポートスキルやリポジトリの安全ルールを上書きしません。相談履歴を自動記録する標準運用では、既存の開始プロンプトを優先してください。

スライドは「仕組みを理解するもの」、この資料は「実際にAIへ渡して進めるもの」です。すべてを順に実行する必要はありません。今の目的に合う枠内だけをコピーしてください。

## 使い方

1. `［ ］` の中を自分の内容に書き換えます。分からない欄は「分かりません」で大丈夫です。
2. 制作するアプリのフォルダを開いた、CodexまたはClaude Codeの制作タスクへ貼ります。
3. AIから質問が来たら、一つずつ答えます。音声でも構いません。
4. 結果を自分で確かめ、「できました」「画面が違います」「ここを変えたい」と返します。

通常のチャットではPC内のファイルやGitHubを操作できない場合があります。その場合は、できたことにせず、制作タスクへの移動や本人の一操作を案内してもらいます。

**入力しないもの：** パスワード、認証コード、APIキー、トークン、秘密鍵、実際の顧客情報。アカウント名を含むパスや非公開URLは、公開Issueへそのまま転載しません。

| 場面 | 使うプロンプト | 最初に許可する範囲 |
| --- | --- | --- |
| 初めてこのPCで作る | 01 初期診断 | 調べるだけ |
| 足りない道具を準備する | 02 セットアップ | 一操作ずつ確認して準備 |
| 他のサービスとつなぐ | 03 連携調査 | 調べるだけ |
| 選んだ連携を試す | 04 接続と小さなテスト | 対象を確認して接続 |
| 成功・失敗を日誌に残す | 05 Issue記録 | 指定先のIssueを作成・追記 |
| 前回の続きを始める | 06 ロード・再開 | 読むだけ。ファイルを戻さない |
| 今日の作業を保存する | 07 セーブ・引き継ぎ | 差分確認後、指定先へ保存 |
| うまくいった方法を再利用する | 08 スキル化 | 手順ファイルの作成 |
| 自分の作りたいものを作り始める | 09 小さなパーツ制作 | 相談後、合意した範囲の制作 |

## 5資料との対応

| スライド資料 | 必要なときに使う依頼 |
| --- | --- |
| 01 座学 | 01で環境を確認し、09で自分の制作を始める |
| 02 GitHub・Cloudflare | 02で不足を準備、05で日誌、07で保存、06で再開 |
| 03 データベース | 09の小さな部分を「架空の予定1件を保存し、開き直す」にする |
| 04 MCP・API | 03で方法を調べ、04で一つ試し、08で成功手順を残す |
| 05 実践FAQ | 下の「うまく進まないときの共通の一言」、06の再開 |

全部の依頼を一度に貼る必要はありません。今やりたいことに合う一つだけ使います。

## 01 初期診断：このPCで何ができるか調べる

入力例：作りたいもの＝予約を一覧で見るアプリ／最初の一部分＝架空の予約3件を表示。

```text
私はアプリ制作の初心者です。この制作に必要な準備ができているか調べてください。

作りたいもの：［目的・使う人］
最初に作りたい小さな部分：［例：架空の予約3件を表示する画面］
使用中のAI：［Codex／Claude Code／分かりません］
制作フォルダ：［パス／このタスクで開いているフォルダ］
GitHubリポジトリ：［URL／まだありません］
Cloudflareへの公開：［今したい／後でよい／分かりません］

今は読み取りだけです。インストール、設定変更、ログイン、公開、課金はしないでください。

確認すること：
1. あなたがこのPCのファイルやコマンドを扱えるか、今どのフォルダを見ているか。
2. OSとバージョン、CPUの種類、メモリ容量、空き容量。GPUは安全に確認できる範囲で調べ、取得できなければ未確認とする。製造番号や端末IDは不要。
3. フォルダ内の案内と構成から、既存アプリ、起動方法、必要な道具を確認する。隠し認証ファイルや秘密情報は読まない。
4. Git、Node.js、Python、GitHub CLI、Wranglerなどについて、存在とバージョンを必要な範囲で確認する。「未導入」と「この制作には不要」を分ける。PythonやGPUを全員の必須条件にしない。
5. GitHubとCloudflareについて、アカウント作成、PC/AIからの認証、対象リポジトリや公開先へのアクセスを別々に確認する。既存のMCP/コネクタの有無と実行可能な操作も確認する。
6. 既に導入されている場合だけ、安全な認証状態の確認を行う。例はgh auth status、導入済みWranglerのwhoami相当。標準出力・標準エラーにはアカウント情報が含まれ得るため、両方を表示せず終了コードだけで確認する。失敗したら未確認とし、生の出力を取得せず原因を一つずつ確認する。確認のためにnpxなどでツールを自動取得しない。

環境変数一覧、認証ファイル、トークンの内容を表示しないでください。結果にはアカウント識別情報を載せず、確認できた状態だけ示してください。
使えるツールがない場合は推測せず、本人が確認できる一操作を案内してください。

結果は「項目／確認済み・未確認・不要／根拠／今の制作への影響」の表にしてください。
最後に、今すぐ作れる最小部分と、必要な準備を分けて示し、次の一操作だけ提案してください。
説明の細かさは操作の様子に合わせ、分からないことは一度に一問だけ聞いてください。
```

**確認すること：** 「アカウントを持っている」と「このAIから使える」が分かれているか。未導入の道具を全部入れようとしていないか。

## 02 セットアップ：足りないところだけ準備する

```text
先ほどの診断結果をもとに、必要な準備を一つずつ手伝ってください。

今回準備するもの：［例：PCからGitHubへ接続する］
制作フォルダ：［パス］
診断結果：［秘密情報を含まない要約／このタスクの直前の結果］

最初にOSと現在の状態を確認し、準備済みの項目はやり直さないでください。
公式の最新手順を調べ、参照URLを示してください。製品名や画面が違う場合は現在の表示を優先してください。
不足する道具のインストールや設定変更の前に、目的・変更先・費用の有無を説明して確認してください。
アカウント作成は本人が行います。Googleで続ける選択肢が実際にあれば案内し、なければ別の公式手順を示してください。
パスワード、認証コード、秘密鍵はチャットへ貼らせないでください。ログインは本人が公式画面で行います。
一度に一操作だけ示し、「成功すると何が表示されるか」も教えてください。
各操作後に結果を確認し、同じ失敗を繰り返す場合は原因確認へ切り替えてください。
この依頼では、D1の作成、アプリ公開、送信、課金、GitHub自動デプロイ設定は行いません。
最後に、準備できたこと・未確認・次にすることをまとめてください。
```

## 03 穴埋め式：MCP／API／ブラウザで連携できるか調べる

入力例：サービス＝Chatwork／したいこと＝指定の部屋の連絡を読み、タスク案を作る／まだしないこと＝投稿・削除。

```text
次のサービスを、このAIから使えるようにする方法を調べてください。今は調査だけです。

サービス名：［Chatwork／Slack／Discord／UTAGE／X／Instagram／その他］
公式サイトURL：［分かれば記入／分かりません］
やりたい操作：［何を読み、何を作り、どこへ保存したいか］
対象：［自分のアカウント／指定の部屋／テスト用データなど］
まだ行わない操作：［例：送信・投稿・削除・購入］
使用AIと環境：［Codex／Claude Code、Mac／Windows、分からなければ調べて］
予算：［無料範囲で試す／月額上限／未定］

次の順に調査してください。
1. 今このAIで利用可能なコネクタ、プラグイン、MCPに目的の機能がないか。
2. 目的を実行できるMCPサーバーがないか。公式を優先するが、非公式も候補に含める。
3. 適切なMCPがなければ、公式APIがあるか。APIキー、OAuth、Botトークンなど実際に必要な認証方式、権限、利用プランを調べる。すべてをAPIキー方式と決めつけない。
4. 適切なAPIがなければ、本人が利用権限を持つ画面をAIがブラウザ操作できるかを調べる。提供規約や自動化の制限を守り、本人確認を回避しない。

「MCPがある」だけで採用せず、今回の読み取り・作成・更新など必要な操作が本当に提供されているか確認してください。
今のAIクライアントで接続可能か、追加設定が必要か、追加費用や回数制限があるかも確認してください。
非公式MCPは、作者・ソース公開・更新状況・データの送信先・要求権限・秘密情報の保管方法を調べてください。確認できない点を明記し、少ない権限とテスト用データで試す案を出してください。
名称が似ているだけの別製品や、古い記事を根拠に接続先URLを推測しないでください。

結果には以下を含めてください。
- やりたい操作ごとの可否：資料で確認済み／実動作確認済み／未確認
- 候補ごとの方式、公式・非公式、提供者、対応操作、認証、費用、注意点
- 確認した公式資料やソースのURLと確認日
- おすすめの方法と理由、使えない場合の代替案
- 最初に試す一つの操作と成功条件

まだ接続、インストール、トークン発行、投稿はしないでください。候補を私が選んでから進めます。
足りない情報は一度に一問だけ聞いてください。
```

**確認すること：** 「読むだけ」「下書きを作る」「実際に送信する」が分かれているか。非公式MCPのリスクが省略されていないか。

## 04 選んだ連携を接続し、一つだけ試す

```text
調査した方法で、次のサービスとの連携を準備してください。

サービス：［名前］
選んだ方法・公式手順URL：［MCP／API／ブラウザ、URL］
対象：［許可されたリポジトリ・テスト用の部屋など］
最初のテスト：［例：指定した一件だけを読む］
成功条件：［例：元の画面と同じ件名・内容が取得できる］

現在の接続状態を調べ、接続済みなら再設定せず、安全な確認へ進んでください。
設定変更やインストールの前に、変更箇所・権限・情報の送信先・費用を説明し、私の確認を待ってください。
秘密情報はチャットやソースに書かず、公式の認証画面または適切な秘密情報の設定先を使います。
手動操作が必要なら一操作ずつ案内し、その後に成功を確認してください。
まず少量の読み取りで試してください。読み取り機能がない場合は、代わりの安全なテストを提案して確認を待ってください。
投稿、送信、削除、公開、課金は別の操作です。対象・内容・影響を見せて、その都度私の明確な確認を取ってください。
エラー時は接続先・権限・設定・利用制限を切り分け、秘密情報は出さないでください。
終了時は、実行した操作、結果、元の画面との照合、未確認の機能を報告してください。接続成功だけで全機能が使えるとは言わないでください。
```

## 05 GitHub Issueへ成功・失敗・解決方法を残す

Issueは作業の日誌です。この依頼は、指定したIssueへの記録をAIに任せるものです。会話を丸ごと転載する依頼ではありません。

```text
このタスクで行った作業を、次のGitHubリポジトリへ作業日誌として記録してください。

記録先リポジトリ：［所有者/リポジトリ名 または URL］
対象Issue：［URL・番号／新規作成／不明なので候補を探して］
今回の目的：［一つの目的］
関連する親Issue：［あればURL／なし］

最初に記録先と公開・非公開を確認し、既存の関連Issueを検索してください。
個人の相談履歴は、自分の非公開リポジトリだけへ記録してください。公開教材リポジトリには書きません。記録先が公開なら投稿せず、非公開の記録先を一つ確認してください。
同じ作業のIssueがあればそこへ追記し、重複作成しないでください。記録先を一意に決められなければ、書く前に私へ確認してください。
指定先へ記録することは許可します。ただし個人情報や秘密情報を含む場合は投稿せず、除いた下書きを示してください。

新規Issueの本文は次の構成にしてください。
# 目的
# 背景・困っていたこと
# 今回行うこと／行わないこと
# 完了条件（チェックリスト）
# 実際に試したこと（順番）
# 成功したこと
# 失敗・エラーと、そのときの条件
# 原因（確認済み／仮説／未確認を区別）
# 解決のために変えたこと
# 確認方法と結果
# 関連ファイル・コミット・資料
# 残っていること／次にする一つ

既存Issueへの追記は、日付、今回の変更、成功・失敗・解決、確認結果、次の一手を一つのコメントにまとめてください。
会話やログを丸ごと貼らず、再現と再開に必要な事実を要約してください。認証コード、トークン、顧客情報、端末の個人名入りパスは載せないでください。
ローカルパス、GitHubユーザー名、メールアドレス、アカウントIDも本文に含めず、関連ファイルはリポジトリ内の相対パスで示してください。
会話から分からない事実や実施していないテストは補完しないでください。ログを根拠にできない場合は未確認と書いてください。
機能が動いたこと、GitHubへ保存したこと、外部公開したことを別々に記録してください。
投稿後にIssueを読み戻して、重複がなく内容が反映されたか確認し、URLを教えてください。投稿結果が不明なら、再投稿前に存在を確認してください。
Issueのクローズ、他のIssueの変更、コードのpushはこの依頼には含めません。
GitHubを操作できない場合は、完成した本文と次の一操作を示し、投稿済みとは言わないでください。
```

## 06 ロード用：前回の作業を確認して再開する

ここでの「ロード」は、前回の状態を理解することです。古いファイルへ戻したり、今ある変更を消したりすることではありません。

```text
前回の続きを始めたいです。まず記録と現在のファイルを読んで、状況を整理してください。

制作フォルダ：［パス／このタスクのフォルダ］
GitHubリポジトリ：［URL／不明］
関連Issue：［URL・番号／不明］
前回の記憶：［覚えていること／覚えていません］
今日やりたいこと：［希望／まず状況を知りたい］

最初に、実際に開いているフォルダとGitHubの記録先が合っているか確認してください。
プロジェクトの案内と作業ルール、関連Issueとコメント、最近のコミット、現在のブランチ、未保存・未コミットの変更、関連ファイルを必要な範囲で読んでください。
別のAIタスクの会話が読めない場合、読めたふりをせず、必要な要約だけ私に聞いてください。
Issueや会話の記録と、現在のファイルが食い違う場合は、その違いを示してください。
「前回の報告」「今ファイルで確認したこと」「動作を再確認したこと」を区別してください。
この段階では、pull、reset、checkout、ブランチ切り替え、ファイルの上書き・削除、インストール、公開はしないでください。
古い状態へ戻す必要があると判断しても、現在の変更を保護する方法を説明し、私の確認を待ってください。

次の順で報告してください。
1. 何を作っているか
2. 前回できたことと、その根拠
3. 現在のファイル・ブランチの状態
4. まだできていないこと、今は未確認のこと
5. 再開するために必要な準備
6. 今日の最初の一操作

最後に「この一操作から進めてよいですか」と確認してください。
```

## 07 セーブ用：作業を保存し、次回の入口を残す

```text
今日の作業を保存し、次回すぐ再開できるようにしてください。

制作フォルダ：［パス］
保存先リポジトリ：［URL／まだない］
関連Issue：［URL・番号／なし］

まず現在の差分、ブランチ、保存先、リポジトリの公開範囲を確認してください。
今回の作業と無関係な変更、秘密情報、認証ファイル、生成物を一括で追加しないでください。
保存予定のファイルと変更の要約を示し、私の確認後に関連ファイルだけコミット・pushしてください。
共同作業のリポジトリはその運用ルールを守り、mainへの直接pushを勝手に行わないでください。個人制作にも不要なPR手順を押し付けないでください。
競合や他の人の変更があれば止まり、強制pushや変更の破棄はしないでください。
リポジトリがない場合は、新規作成の名前・所有者・非公開設定を提案して確認してください。
「PCに保存」「コミット済み」「GitHubへ反映済み」を分けて確認してください。push後はリモート側のコミットを確認し、URLを教えてください。
DBのデータ、外部サービス設定、秘密情報がGitHubへの保存だけでは保管されない場合は、その範囲も説明してください。
最後に、できたこと・動作確認・開くフォルダ・関連Issue・未完了・次に渡す一文を、秘密情報のない再開メモにしてください。
Issueへの追記や追加ファイルへの保存が必要なら、保存先を示して確認してください。
```

## 08 成功した方法をスキルとして残す

```text
今回うまくいった作業を、次もAIが再利用できる手順にしてください。

再利用したい作業：［例：指定のChatworkルームを読み、未送信のタスク案を作る］
成功した記録のIssue：［URL］
保存先フォルダ・リポジトリ：［パス・URL］
使うAI：［Codex／Claude Code／両方］

最初に既存のスキルと保存ルールを確認し、同じ目的のものがあれば更新してください。
利用するAIの現行仕様を確認して、適切な場所と形式で作成してください。保存しただけで自動的に読み込まれるとは判断しないでください。
手順には、目的、使う場面、必要な接続・権限、入力、操作順、成功条件、エラー時の分岐、中止条件を含めてください。
送信・削除・公開など本人確認が必要な箇所を明記してください。キーやトークンの実値は書かず、安全な設定先の説明だけを残してください。
一度成功した条件と未検証の条件を区別し、サービスやOSが変わっても必ず動くとは書かないでください。
小さな読み取りテストで再利用できるか確認し、確認できなければ未検証と記録してください。
作ったファイル、呼び出し方、テスト結果、残る注意点を報告してください。
GitHubへのpushとIssueへの投稿は、内容・保存先を示して私の確認を得てから行ってください。
```

## 09 自分の作りたいものから、小さなパーツを作る

今日の目標は、アプリ全体の完成ではなく、希望を伝え、動く一部分を見て、もう一度変更を頼めることです。

```text
私は、AIと相談しながら自分のアプリを作り始めたいです。
まず話を整理し、今日試せる小さな一部分を一緒に決めてください。

誰が使うか：［自分／お店のスタッフ／その他］
今はどうしているか：［紙や表に書いている、など］
何が面倒か：［困っていること］
どうなるとうれしいか：［理想］
画面で見たいもの：［一覧、ボタン、入力欄など／分かりません］
好きな雰囲気：［色・参考画面／おまかせ］
制作フォルダ：［今開いているフォルダ／パス／分かりません］
今日使える時間：［分］

言い間違いや順番が前後した話も、意味を整理してください。
分からないことは一度に一つだけ質問してください。
既存のフォルダと使える道具を確認し、今ある作品を勝手に上書きしないでください。

最初に、次の3点を提案してください。
1. 今日作る一部分（例：架空の予定3件を一覧にする）
2. 今回は作らない部分（例：本物のカレンダー接続、ログイン、公開）
3. 私が画面で確認できる成功条件

私がその案を選んだら、合意した一部分を作ってください。
新たなインストール、外部接続、課金、公開が必要なら、先に説明して確認してください。
本物の個人情報ではなく、架空のデータを使ってください。
画面だけの見本、動く機能、保存できるデータを区別してください。
保存機能を作る場合は、再読み込みや開き直し後にも残るか確認してください。

動いたら、私が開く画面と確認する操作を一つずつ案内してください。
その後、「見てみて、どこを変えたいですか」と聞いてください。
私の感想をもとに一か所直し、もう一度確かめるところまで手伝ってください。
最後に、できたこと、未確認、次に試す一つをまとめてください。
GitHubへの保存や公開は、完了したと推測せず別に確認してください。
```

**体験できたかの確認：** 自分で一つ希望を伝え、結果を見て、一つ追加の変更を頼めたら、この練習の目的を達成しています。アプリ全体の完成や公開は、その先の段階です。
