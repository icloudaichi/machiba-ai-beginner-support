# 運営がprivate repoの進捗を確認する

和佐さん・下山さんなどの運営が、参加者の表示名ごとに相談履歴と進捗を確認するには、参加者自身のprivate app repoへ運営のGitHubアカウントをcollaboratorとして招待する必要がある。

公開教材repoや公開Issueへ個人ログを集約しない。

## 招待前に伝えること

collaboratorは相談Issueだけに限定された閲覧者ではない。GitHubの招待画面で示される権限に応じて、private repo内の次の情報へアクセスできる。

- アプリのコードとcommit履歴
- AI相談Issueと相談履歴
- ほかのIssue、branch、設定の一部
- repoへ追加されたファイル

参加者へ、対象repo、招待するGitHubユーザー名、付与する権限、確認目的を示す。相談履歴の標準開始プロンプトは、collaborator招待を承認するものではない。招待ごとに本人の明示了承を得る。

## 確認する情報

- 参加者が希望する表示名
- 参加者自身のprivate app repoであること
- 招待先の正確なGitHubユーザー名
- GitHub画面に表示される権限範囲
- 招待後に誰がアクセスできるか

メールアドレスだけで対象を推測しない。運営本人からGitHubユーザー名を確認し、似たアカウントを招待しない。

## 招待の流れ

1. 参加者へ、運営が相談履歴を確認する目的を説明する。
2. 対象repo、運営GitHubユーザー名、権限を提示する。
3. 参加者から明示了承を得る。
4. GitHubのprivate repo設定からcollaboratorを招待する。
5. 招待が受諾されたことを、private repoのアクセス管理画面で確認する。
6. 相談Issueを開けることを運営本人が確認する。

招待操作をAIへ依頼する場合も、対象repo、ユーザー名、権限、影響を提示し、実行直前に本人の確認を得る。標準の自動相談記録と同じ承認で実行しない。

## 運営の確認方法

各参加者のprivate repoで、CLIが作成した`AI相談｜表示名｜日付`Issueを確認する。表示名はprivate repoのIssueタイトルと本文に入る。相談コメントには次が構造化される。

- 相談内容と背景
- 試したことと失敗
- 解決方法と学び
- 次の一手
- 関連commit
- 成果物を提出した場合のファイル名、経路、指定フォルダの親・ファイル名をDriveで確認した結果
- Drive確認済みとは別の、GitHub Issue記録のread-back状態と次の一手
- 確認できた場合だけ成果物の個別Drive URL

運営は会話全文ではなく、構造化された現在地を読む。質問や補足をIssueへ書く場合も、個人情報、秘密情報、生のエラー出力を書かない。

## 招待しない・解除する場合

参加者が招待を希望しない場合も、講座への参加やローカル制作を続けられる。運営が見られない個人ログを、公開教材repo、公開Issue、外部チャットへコピーして代替しない。

講座終了後のアクセス継続は別途方針を決める。解除する場合も、対象アカウント、影響、タイミングを参加者へ確認してから行う。招待解除は相談履歴Issueやコードを削除する操作ではない。
